# Device QA status

**Real iOS/Android hardware verification: still an open gap, not resolved.** game-debugger had no Xcode/iOS Simulator, no adb/Android emulator, and no device-farm (BrowserStack) access, and correctly declined to toggle Safari's systemwide Remote Automation setting itself. It ran Playwright's real WebKit engine (genuine Apple WebKit, not Chromium) at an iPhone 13 viewport as the closest available proxy.

**Passed under the WebKit-engine proxy:** drag pick-up/follow/drop, corner/boundary placement, off-canvas release, `pointercancel` mid-drag, `touch-action:none`/`overscroll-behavior:none` computed styles, no horizontal overflow at 390px, visual rendering. No fix needed.

**Still unverified, cannot be verified without real hardware:** elastic overscroll, edge-swipe-back, Dynamic Island/safe-area handling, genuine OS-level multi-touch gesture routing, and specifically whether touch-drag triggers page-scroll on real hardware (synthetic PointerEvents don't route through the OS gesture recognizer the way real touch does).

**Decision (project-manager call):** accept the WebKit-proxy pass as sufficient confidence to continue pre-production/design work. Do not block the project on hardware access at this stage — the core mechanic doesn't depend on device-specific gesture quirks, and a scroll-hijack bug found later is fixable, not a redesign risk. **Defer true real-device verification to release-manager's export/build stage**, where it becomes unavoidable anyway (an actual packaged mobile build is a stronger, more meaningful thing to test on real hardware than a bare local-server HTML prototype). Non-blocking suggestion carried over from the debugger's report: consider `-webkit-touch-callout: none` on the canvas/stage-wrap at that point, though likely unnecessary since `<canvas>` isn't normally subject to iOS's long-press callout.

## Capacitor build-stage pass (2026-07-26)

Capacitor wrap scaffolded (`capacitor.config.json`, `android/`, `ios/`; web assets copied into `www/` as the `webDir` so the native shells don't bundle `node_modules`). **Android: built and ran.** `./gradlew assembleDebug` succeeded; installed and launched on a locally-booted `android-34/google_apis/arm64-v8a` emulator (Pixel 6 profile, 1080x2400 @420dpi, so DPR ~2.6x — a real high-DPI proxy). **Touch-drag QA: inconclusive, not a pass.** `adb shell input swipe` from tray to board did not register as a piece placement at any duration tried (300ms/500ms/1500ms), and a 1500ms swipe was instead consumed as a system-level gesture (kicked the app to the home launcher) rather than reaching the WebView as a drag. Before this could be root-caused, the emulator's System UI itself hit an ANR ("System UI isn't responding"), which lined up with the host disk having been driven down to ~800MB free by the SDK/emulator install (freed back up to ~4.3GB by removing an unrequested auto-installed build-tools 35/platform 36 and clearing gradle/homebrew caches). **So the failed drag reproduction cannot be trusted as a real app bug** — it's confounded by a resource-starved, software-rendered (swiftshader), disk-pressured emulator, exactly the kind of non-hardware artifact this doc already warned about. Orientation-change-mid-drag (the specific case PM flagged re: issue #1/endDrag) was not reached before wrapping for the same reason.

**Still open:**
- Real touch-drag and orientation-change-mid-drag verification on Android — needs either a real Android device over adb (a real finger/stylus touch, or `adb shell input draganddrop` with correctly-tuned coordinates for `dragTargetCell()`'s -40px vertical offset) or a healthier, hardware-accelerated emulator with headroom, not the constrained one available here.
- iOS build/QA entirely — needs full Xcode.
- If this environment is reused for further Android QA, budget more free disk up front (the full toolchain + one system image is ~8GB) and prefer `-gpu host`/hardware acceleration over swiftshader if the host supports it, to avoid System-UI-level instability muddying results.

## Android touch-drag + orientation-change retry (2026-07-26, later same day)

**Environment was clean this time — confirmed before starting, not assumed.** Host disk had 25Gi free (`df -h /`), no cleanup needed. SDK at `/opt/homebrew/share/android-commandlinetools` had exactly one build-tools version (34.0.0) and one system image (android-34/google_apis/arm64-v8a) — no stray build-tools 35/platform 36 bloat this time, so no removal was necessary. Booted the same `fracture_test` AVD (Pixel 6 profile, android-34/google_apis/arm64-v8a) but edited `~/.android/avd/fracture_test.avd/config.ini` to set `hw.gpu.enabled=yes` / `hw.gpu.mode=host` and launched with `-gpu host` explicitly (confirmed `emulator -accel-check` reported Hypervisor.Framework available first). Boot completed in ~6s with no System UI instability, no ANR, at any point in this session. `./gradlew assembleDebug` succeeded (JDK 21 needed to be pointed at explicitly via `JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home` — `/usr/libexec/java_home -v 21` silently fell back to the system JDK 8 because the Homebrew-installed JDK was never registered with `java_home`; this is an environment quirk worth remembering for future sessions here, not a project bug). APK installed and launched cleanly via `adb install -r` + `adb shell am start`.

**Touch-drag placement: PASS, confidently, not inconclusive.** `adb shell input swipe <trayX> <trayY> <boardX> <boardY> 700` reliably registered as a real drag-and-drop through the WebView twice in a row: a 1×2 red piece and a 1×2 blue piece both landed in the exact target cells (confirmed via screenshot: piece rendered at the intended row/col, score incremented 0→2→4, tray slot emptied each time). No home-launcher-gesture hijacking this time — unlike the previous attempt's 1500ms swipe getting eaten as a system gesture, 700ms swipes at these coordinates were interpreted as an in-app touch drag every time. Coordinates were derived from a `screencap` of the running app (real device pixels, 1080×2400) plus a manual compensation of the `dragTargetCell()` -40px vertical rendering offset baked into `src/main.js` (`oy = drag.y - (rows*s)/2 - 40`) — i.e. aim the swipe endpoint ~48 physical px *below* the visual center of the intended cell/cell-pair, since the piece renders lifted above the finger. This is a real, repeatable pass on hardware-accelerated `-gpu host`, not a fluke of one lucky duration/coordinate combo.

**Orientation-change-mid-drag: reached and tested, PASS with a caveat about how it was exercised.** Used `adb shell input motionevent DOWN/MOVE/UP` (discrete, not `swipe`) to hold a touch down mid-drag — confirmed via a mid-gesture screenshot that the drag was genuinely live (dragged piece rendering under the pointer, red invalid-drop overlay showing over occupied cells). While that touch was still down (no UP sent), rotated the emulator portrait→landscape via `adb shell settings put system accelerometer_rotation 0` + `adb shell settings put system user_rotation 1`. Result: no crash, no ANR, no `AndroidRuntime` fatal exceptions in logcat, and no JS exceptions in logcat around the rotation window. The in-flight piece did **not** get stuck, duplicated, or lost — it reappeared safely back in its original tray slot, consistent with the app's existing `canvas.addEventListener('pointercancel', () => { drag = null; draw(); })` handler firing when the WebView surface is recreated on rotation (this is the expected/designed recovery path referenced by the `endDrag()` comment re: issue #1, and it held up under an actual rotation, not just a code trace). Board state (score, previously-placed pieces) was byte-for-byte unchanged across the rotation. Follow-up checks: **(a)** placed a fresh piece successfully in landscape orientation afterward (confirms the post-rotation layout/coordinate recompute is not just non-crashing but fully functional, not just inert), **(b)** rotated back landscape→portrait and confirmed the board rendered correctly with all previously-placed pieces intact and no residual landscape-layout artifacts.

**Caveat on this pass, stated plainly:** `input motionevent DOWN/MOVE/UP` synthesizes a held pointer at the Android input-framework level, which is a reasonable proxy for "finger physically still on the glass during a rotation," but it is not the exact same code path as a continuous real-hardware touch sensor stream — a real device could in principle deliver a differently-shaped event sequence around the rotation boundary. Given the app's behavior matched the designed `pointercancel` recovery path exactly and no divergent behavior showed up, this is a confident pass for the code path in question, but real-device confirmation (not just real-emulator) remains the gold standard and is still the one thing this session couldn't provide.

**Root-cause takeaway on the previous session's failure:** this retry confirms the prior "touch-drag did not register" result was indeed the resource-starved/swiftshader emulator artifact suspected at the time, not a real app bug — same app code, same AVD profile, only the disk headroom and `-gpu host` vs. swiftshader differed, and touch-drag worked immediately and repeatably here.

**Still open:**
- iOS build/QA entirely — still needs full Xcode, unchanged from before.
- Real-hardware (non-emulator) confirmation of both touch-drag and orientation-change-mid-drag remains the gold standard; this session raises confidence considerably (from "inconclusive" to "passing on a healthy hardware-accelerated emulator, twice, with a clean root-cause explanation for the earlier failure") but a real device/BrowserStack-style farm pass is still the strongest remaining verification gap.
- Not tested this session: rapid repeated drags, drag-and-release exactly on a board boundary/edge cell, and a drop that triggers a row/column clear + shard-queue scatter concurrently with a rotation (the orientation test used a drop that was rejected/cancelled, not one that completed a clear) — worth covering in a future pass if the shard-scatter animation/timer logic has its own rotation-sensitivity.
