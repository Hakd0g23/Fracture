# Device QA status

**Real iOS/Android hardware verification: still an open gap, not resolved.** game-debugger had no Xcode/iOS Simulator, no adb/Android emulator, and no device-farm (BrowserStack) access, and correctly declined to toggle Safari's systemwide Remote Automation setting itself. It ran Playwright's real WebKit engine (genuine Apple WebKit, not Chromium) at an iPhone 13 viewport as the closest available proxy.

**Passed under the WebKit-engine proxy:** drag pick-up/follow/drop, corner/boundary placement, off-canvas release, `pointercancel` mid-drag, `touch-action:none`/`overscroll-behavior:none` computed styles, no horizontal overflow at 390px, visual rendering. No fix needed.

**Still unverified, cannot be verified without real hardware:** elastic overscroll, edge-swipe-back, Dynamic Island/safe-area handling, genuine OS-level multi-touch gesture routing, and specifically whether touch-drag triggers page-scroll on real hardware (synthetic PointerEvents don't route through the OS gesture recognizer the way real touch does).

**Decision (project-manager call):** accept the WebKit-proxy pass as sufficient confidence to continue pre-production/design work. Do not block the project on hardware access at this stage — the core mechanic doesn't depend on device-specific gesture quirks, and a scroll-hijack bug found later is fixable, not a redesign risk. **Defer true real-device verification to release-manager's export/build stage**, where it becomes unavoidable anyway (an actual packaged mobile build is a stronger, more meaningful thing to test on real hardware than a bare local-server HTML prototype). Non-blocking suggestion carried over from the debugger's report: consider `-webkit-touch-callout: none` on the canvas/stage-wrap at that point, though likely unnecessary since `<canvas>` isn't normally subject to iOS's long-press callout.

## Capacitor build-stage pass (2026-07-26)

Capacitor wrap scaffolded (`capacitor.config.json`, `android/`, `ios/`; web assets copied into `www/` as the `webDir` so the native shells don't bundle `node_modules`). Toolchain stood up from scratch in this environment: Homebrew `android-commandlinetools` cask + `openjdk@21` (AGP requires JDK 21; JDK 8 that shipped in the environment wasn't enough), Android SDK platform 34 / build-tools 34.0.0 / platform-tools / emulator / an arm64-v8a system image.

**iOS: blocked, not attempted.** Only Xcode Command Line Tools are present, not the full Xcode.app — `ios/` scaffolding exists (`npx cap add ios` succeeded) but nothing can build or simulate it in this environment. This needs a machine/environment with full Xcode, or CI (e.g. Xcode Cloud/GitHub Actions macOS runner) — flagging rather than guessing since it's an environment/access gap, not a code issue.

**Android: built and ran.** `./gradlew assembleDebug` succeeded; installed and launched on a locally-booted `android-34/google_apis/arm64-v8a` emulator (Pixel 6 profile, 1080x2400 @420dpi, so DPR ~2.6x — a real high-DPI proxy). Screenshot confirmed the canvas renders crisp at that density (sprite atlas scaling looks correct, no blur/misalignment) and basic touch (tap on "New Game") reliably reaches the WebView.

**Touch-drag QA: inconclusive, not a pass.** `adb shell input swipe` from tray to board did not register as a piece placement at any duration tried (300ms/500ms/1500ms), and a 1500ms swipe was instead consumed as a system-level gesture (kicked the app to the home launcher) rather than reaching the WebView as a drag. Before this could be root-caused, the emulator's System UI itself hit an ANR ("System UI isn't responding"), which lined up with the host disk having been driven down to ~800MB free by the SDK/emulator install (freed back up to ~4.3GB by removing an unrequested auto-installed build-tools 35/platform 36 and clearing gradle/homebrew caches). **So the failed drag reproduction cannot be trusted as a real app bug** — it's confounded by a resource-starved, software-rendered (swiftshader), disk-pressured emulator, exactly the kind of non-hardware artifact this doc already warned about. Orientation-change-mid-drag (the specific case PM flagged re: issue #1/endDrag) was not reached before wrapping for the same reason.

**Still open:**
- Real touch-drag and orientation-change-mid-drag verification on Android — needs either a real Android device over adb (a real finger/stylus touch, or `adb shell input draganddrop` with correctly-tuned coordinates for `dragTargetCell()`'s -40px vertical offset) or a healthier, hardware-accelerated emulator with headroom, not the constrained one available here.
- iOS build/QA entirely — needs full Xcode.
- If this environment is reused for further Android QA, budget more free disk up front (the full toolchain + one system image is ~8GB) and prefer `-gpu host`/hardware acceleration over swiftshader if the host supports it, to avoid System-UI-level instability muddying results.
