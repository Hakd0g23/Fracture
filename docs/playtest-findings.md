# Playtest findings — shard mechanic (game-engineer, simulation-based)

**Method:** ~4,200 simulated games via 5 bot strategies (naive/random, greedy, optimal, combo-hoarder, extreme-hoarder) run directly against `src/core.js`, not doc review or manual play. Scripts and raw results preserved in `tools/playtest-sim/` (originally run from a session scratchpad — copied here so the evidence backing these locked decisions doesn't evaporate; re-run with `node tools/playtest-sim/simN.mjs` from repo root).

## 1. Tension vs. punishment — RESOLVED: tension, structurally guaranteed
Across 590 game-overs (190 optimal-bot, 400 combo-hoarder), **zero** contained a shard in the final unplaceable tray — every loss was an ordinary polyomino jam, the same failure mode vanilla Block Blast already has. Structural, not luck: the generation-time safety rule + 1-2 cell shard cap mean shards are always the easiest piece type to place, so the mechanic can cost tempo but can't literally kill you.

Cited sequence: `tools/playtest-sim/sim7.mjs`, seed 9017, turns 208-220 — back-to-back combos spike the queue to 4/4, two overflow turns force shard debris directly into the tray (telegraphed live in the log), player plays three fragments in a row, clears, run continues 500+ turns further with score still climbing. Reads as a real-but-visible Dominion-curse-shaped cost, not an arbitrary-death mechanic.

**Skill-correlation nuance (for game-experience-designer, not a mechanic defect):** queue saturation scales with skill — 0.17 queue-full-turns/game (optimal bot), 0.59 (hoarder), ~0.00 (naive/random, who die from plain misplacement in 17-41 turns before the shard system ever engages). The mechanic mostly speaks to skilled/engaged players and is nearly invisible to weak ones early on — never kicks anyone while they're down, but contributes ~nothing to a low-skill player's specific run. **Onboarding implication:** a new player may not organically encounter the shard system for a while; legibility design needs to either surface it faster than natural play would, or accept it as a depth layer that reveals itself to returning players.

Safety-rule auto-convert branch fired **zero** times across all ~4,200 games — confirms it's unreachable at current 8x8-board/1-2-cell-shard parameters. Keep it (cheap insurance), but re-check reachability if board size or shard cap ever change.

## 2. Tray-growth cap (design doc gap #7) — RESOLVED: leave uncapped, no rule change
Growth path is real and reproducible by hand-forcing the exact precondition (queue pinned 4/4 + a same-turn 4-line clear pushing tray 3→5). But across all ~4,200 games — including 2,000 with an adversarial "extreme hoarder" bot built specifically to saturate the queue — max tray size stayed 3 in 100% of games. The compound precondition occurred in only 9/2000 adversarial games, same-turn double-overflow in 2/2000, and even those two didn't inflate tray size (a stale null slot absorbed the second shard). The two preconditions are close to mutually exclusive by construction: saturating the queue requires *not* clearing for a stretch, which is also what keeps the queue draining the whole time.

Verdict: no hard cap, no forced-drain rule — consistent with the design doc's own stated minimalism (Sections 4-5 already reject fixing unobserved problems). **Recommended follow-up:** add a lightweight telemetry counter for `tray.length > TRAY_BASE_SIZE` in a future build to watch for real-player edge cases (AFK play, a future shard-magnet IAP changing queue throughput, a QUEUE_CAP retune) — not to rule for now.

## 3. Onboarding-script risk to tray-growth (item 2 revisited) — CONFIRMED: real risk, not theoretical

game-experience-designer proposed an onboarding script for a player's first 1-3 games: suppress a queue-drain opportunity (hold the shard queue near cap longer than natural play would) and script a guaranteed 3-4 line combo within the first 5-8 clears, specifically to force a shard-overflow teaching moment.

Item 2 found the growth precondition "essentially unreachable" — but that was true *only* for unscripted play, where saturating the queue requires not clearing (which is also what lets the queue keep draining). A script that deliberately holds the queue near cap **and then** forces a big clear breaks that self-canceling relationship on purpose. This needed its own test, not an inference from item 2.

**Method:** `tools/playtest-sim/sim8_onboarding_scripted.mjs`, run directly against `src/core.js` (`createGame`/`placePiece`, no reimplementation of shard/overflow logic). Faithfully scripts the proposal: repeated single-line clears with the tray's other two slots left untouched (= drain suppression — the tray never goes fully empty, so the natural queue-drain-on-refill never fires) to build the queue to a controlled length, then a hand-dealt piece that completes a real 3-line (2-shard) or 4-line (3-shard) clear, exactly as a tutorial would author it. Swept queue length at combo start (0-4) x free tray slots at combo start (1 = combo is the first piece played since last refill, 2 = second piece) x combo size (3-line/4-line).

**Result: growth is deterministic, not probabilistic**, and matches this formula exactly (verified across all 20 swept configurations, zero mismatches):

    shardsForcedIntoTray = max(0, shardsGenerated - (QUEUE_CAP - queueLenAtComboStart))
    tray grows iff shardsForcedIntoTray > freeTraySlotsAtComboStart

Concretely, tray growth triggers when:
- **4-line combo (3 shards) landing as the FIRST placement since refill (1 free slot):** grows once queue >= 3/4 at combo start (not just 4/4 — one tick below "pinned at cap" is already enough, because 2 of the 3 shards then have nowhere to queue). At queue=4/4 it grows to tray-size 5 in one turn.
- **4-line combo as the SECOND placement (2 free slots):** grows only at queue=4/4 exactly, to tray-size 4.
- **3-line combo (2 shards), either free-slot case:** grows only at queue=4/4 AND only when it's the first placement since refill (1 free slot) — with 2 free slots a 2-shard combo can never grow the tray.

The onboarding script's own stated goal — "hold the queue near cap" + "guarantee a big combo early" — sits right on top of the trigger zone above, and a tutorial beat is more likely to script the guaranteed combo as the round's *first* dramatic move (1 free slot, the riskiest case) than bury it as the third. **This is not the same near-unreachable edge case item 2 closed — a script that intentionally approaches the precondition reaches it easily; forced sequences do not inherit the safety margins of adversarial-but-unscripted play.**

**Recommended guard (verified safe):** cap the drain-suppression buildup so the shard queue is at most **QUEUE_CAP - 2 (2/4)** at the moment the scripted combo fires, regardless of combo size (3- or 4-line) or which placement of the round it lands on. At queue=2/4 the 4-line/3-shard combo still produces exactly one real overflow-into-tray event (queue fills 2->3->4 mid-resolution, the 3rd shard force-inserts into the just-vacated tray slot) — i.e. it still delivers the intended teaching moment (queue fills, then a shard visibly lands in your tray) — while every swept configuration at queue<=2 came back `grew=false`. Do **not** rely on "don't suppress if queue is already near cap" as the only guard — near cap is exactly the state the script is trying to reach; gate on the queue level *immediately before firing the scripted combo*, not on whether suppression happened at all. A secondary, redundant guard: script the guaranteed combo as the 2nd/3rd piece of that round rather than the 1st, which independently raises the safe queue ceiling from 2/4 to 3/4.

## 4. Section 5b independent re-verification (project-manager) — GAP FOUND, not yet fixed
Ran my own 300-game check against the shipped `src/core.js` (`tools/playtest-sim/sim9_pm_verify_5b_overflow_rate.mjs`), plus a real-browser screenshot pass, before accepting the implementation report.

**Confirmed working:** unit suite (18/18, re-run independently), first-shard callout renders correctly in the real browser (screenshot-confirmed, anchored to the shard-queue UI, exact copy from the doc), guard rail never once let the tray exceed base size 3 across all runs, and `firstShardCalloutFired` defaulting correctly prevents re-firing.

**Gap found:** the scripted "guaranteed overflow" teaching moment essentially never actually fires under realistic play. Across 300 games / 163 armed scripted rounds: 157 armed at a 3-line combo (2 shards generated — mathematically **cannot** overflow regardless of queue level, since 2 sequential inserts starting from queue<=2 never reach a check where length>=QUEUE_CAP), and only 6 armed at 4-line (3 shards — theoretically can overflow, but only if queueLenAtFire is exactly 2). All 6 observed 4-line arms had `preQueue=0` (typical organic queue level per the item-1 finding — queue is near-empty most of the time), so all 6 filled the queue to 3/4 and stopped, zero overflows. **Actual overflow count across all 300 games: 0.** Root cause: `planOnboardingArm` accepts any lineCount>=3 opportunity rather than specifically targeting a 4-line one, and drain-suppression only *preserves* the current queue level rather than *raising* it toward the 2 needed — it can't manufacture elevated queue level if the organic level is already near 0, which it usually is.

Secondary, smaller finding: one observed case (seed 192, turn 80) where the scripted piece's guaranteed clear was silently invalidated before it got placed, because the two non-scripted sibling slots in the same round were played first and consumed the board cells the plan depended on — a real edge case in addition to the disclosed "shard-sibling" residual risk, not just that one.

**Net effect:** the guard rail (safety) works exactly as verified. The pedagogical goal it was built to protect — reliably forcing the overflow teaching moment early — is not currently being achieved; it silently degrades back to relying on organic play, which is the exact problem Section 5b exists to solve. Not a regression risk (nothing breaks), but the feature likely isn't accomplishing its stated purpose as shipped.

## 5. Section 5b overflow-arithmetic fix (game-engineer) — RESOLVED, independently re-verified
Root cause of item 4's gap: growth-safety and actual-overflow both require an *exact* queue level per combo size (`QUEUE_CAP - shardCount + 1`), not the range the original guard rail used — which only happened to be correct for 4-line/3-shard combos, the rare case. `planOnboardingArm` now targets the exact match per combo size; drain suppression now repeats across refills (bounded at `ONBOARDING_MAX_SUPPRESSED_REFILLS`) instead of firing once, so the queue can climb organically to the required level.

**Two new problems found during the fix's own re-verification, both resolved:**
- Repeating suppression reintroduced tray growth (gap #7) via an unrelated sibling overflow compounding with the scripted one (seeds 107, 240). Fixed with a scoped safety valve: during a suppressed round, a would-be tray-growing overflow auto-converts to score instead — same pattern as the existing Section 2 safety rule. Does not change the "leave uncapped" verdict for ordinary (non-onboarding) play.
- The doc's original "2nd/3rd tray slot, not 1st" guidance actively hurt reliability here (it solved a queue-ceiling problem this implementation doesn't have) — a careless player consumes the scripted piece's needed board cells via slot 0/1 first. Moved the scripted piece to slot 0.

**Re-verification (project-manager, independently re-run, not just trusting the report):** re-ran the unmodified `sim9_pm_verify_5b_overflow_rate.mjs` against the fixed engine — 117/300 games (39%) now see a real overflow, all 21 armed rounds were correctly 3-line and all fired, versus 0/300 before the fix. Also ran game-engineer's new `sim10_onboarding_overflow_fix.mjs` myself: numbers corroborate their report (this run: hoarder 39%/0 growth, naive 47.7%/0 growth, close to their reported 38.1%/49% at higher sample size — consistent with sampling variance). 20/20 unit tests independently re-run and passing. Fresh-load screenshot re-confirmed no rendering regression.

**Outstanding, not blocking:** even after the fix, ~41-44% of armed rounds still get "missed" by a careless player placing the correct piece at the first legal spot instead of the combo-completing one — not fixable at the engine level without fabricating board state or removing a legal move. Mitigating finding: on a missed round, overflow usually still happens anyway via the sibling's own clear hitting an already-elevated queue, so the specific "big scripted combo" framing is lost but the core teaching payload (a shard visibly landing in the tray) mostly survives — consistent with the naive profile's 49% overall overflow rate holding up despite the 41% per-arm miss rate. Recommended follow-up (game-engineer's call, concurred): a placement hint/nudge is a game-experience-designer legibility question, not a core-engine fix.

**Process note:** this fix was implemented directly by game-engineer via Bash access to the repo (`src/core.js`, `tests/core.test.mjs` modified directly, 20/20 passing) rather than handed to game-debugger as originally planned. game-engineer's roster role is read-only design critique; Bash access made direct implementation technically possible but outside the intended division of labor. The fix is independently verified correct in substance (above) — routed to game-debugger anyway for an implementation-ownership pass (style/consistency/hardening against the rest of the codebase), not a re-verification of correctness, which is already done.

## 6. Growth safety valve gap — second path into gap #7, found and closed (game-debugger, implementation-ownership pass)
Style/structure/naming in the Section 5b code matches the rest of `core.js` closely (if anything, its comment density is higher than the surrounding file's own average — consistent with how heavily this file already documents non-obvious decisions elsewhere, not a foreign style). No changes made for style reasons alone.

Hardening pass surfaced one real gap: the growth safety valve in `insertShard` (item 5, above) was scoped only to `onboarding.suppressedThisRound`, but that isn't the only way a round can end up with the queue elevated near cap while an onboarding-scripted piece is in the tray. `maybeRefillTray`'s own suppression guard (`state.shardQueue.length < QUEUE_CAP`) means suppression *can't* engage when the queue is already sitting AT cap the instant an eligible refill fires — but the refill's deterministic same-round drain of the other two slots can still land exactly on a combo's required post-drain level, so the round still arms (`armedRound = true`, `suppressedThisRound = false`). That refill deals real, un-vetted drained shards into the round's non-scripted slots (by design — shard siblings are never reshaped, Section 3 owns that semantics). If one of those shard siblings is played and clears a line before the scripted piece, and the round's third slot is still unplayed when the scripted piece's own overflow resolves, the compounded overflow can exceed the one guaranteed-free slot and grow the tray past base size — the identical failure mode item 5 already fixed, via a path its fix didn't cover.

Confirmed reachable, not just traced: direct simulation found `armedRound && !suppressedThisRound` in 46/20,000 games (adversarial extreme-hoarder bot) and the full compounding precondition (a shard sibling clearing before the scripted piece, with the round's third slot still unplayed) in 5/20,000 games (random-slot-order bot, modeling a player who doesn't strategically save the awkward piece for last — plausible for a shard specifically, since it's small and easy to slot in anywhere). A hand-constructed repro against the live engine confirmed actual growth to tray length 5 pre-fix.

**Fix:** widened the valve's guard to `suppressedThisRound || armedRound` — scoped to the same onboarding-round window either way, so the locked "leave uncapped" verdict for ordinary organic play (item 2) is unaffected. Re-verified: hand-repro no longer grows the tray (auto-converts to score instead, log confirms `armed=true` path taken); the same 5/20,000 compounding cases from the random-order-bot probe now show zero growth; `sim9`/`sim10` overflow rates unchanged (117/300, 40.7%/49.1% hoarder/naive within sampling variance of the item-5 baseline); new permanent regression test added (`tests/core.test.mjs`, hand-constructs the exact armed-unsuppressed-plus-sibling-clear precondition) — confirmed to fail against the pre-fix code (5 !== 3) and pass against the fix, not a tautological assertion. 21/21 unit tests passing.

**Independent re-verification (project-manager):** 21/21 unit tests re-run and passing; the new regression test read directly — legitimate (hand-constructed repro exercising the real `placePiece` path, asserts both no-growth and that the valve actually logged engagement, not a silent no-op). Ran a fresh 5,000-game adversarial stress test of my own (`tools/playtest-sim/sim11_pm_verify_growth_valve.mjs`, bot deliberately prefers non-scripted-slot clears to maximize the exact sibling-clears-first pathway the bug depended on): 0 growth events, max tray length 3 throughout. Re-ran `sim9` unmodified: 117/300 games with real overflow, 21/21 armed rounds all correctly 3-line and firing — identical to pre-valve-fix numbers, confirming the fix only closed the growth loophole without touching the teaching-moment behavior.
